# Dify Design Lessons for Drucker

## 目标

这份文档不讨论 Dify 的具体代码实现优劣，也不建议照搬其 API 选择、参数设计或技术栈。重点只看它作为成熟 AI 平台在架构设计上的可借鉴之处，并结合当前 Drucker 的现状做选择性提炼。

## 先说结论

Dify 最值得学习的，不是某个模型 SDK 接法，而是它把 AI 系统拆成了几层彼此独立的“稳定对象”：

- 用户交互层：消息、会话、应用入口
- 执行层：一次 run，以及 run 内部的 step / node / tool 调用
- 模型接入层：统一模型抽象、provider 配置、凭证管理、模型选择
- 观测层：日志、成本、耗时、状态、外部 tracing

对 Drucker 来说，真正有价值的是这种分层思路。当前 Drucker 的主要问题不是“用 OpenAI 还是 Gemini”，而是很多核心概念还混在一个 agent 循环里，导致模型切换、运行追踪、回放分析都变得很重。

## Drucker 当前状态的本质

基于现有总结，可以把 Drucker 的现状概括成三点：

1. 会话和执行状态主要存在内存里，而不是稳定持久化对象里。
2. Agent 编排、模型调用、工具调用、SSE 输出耦合在一起。
3. 业务层直接依赖 OpenAI 的 Responses API 语义，而不是依赖平台自己的统一模型语义。

这意味着当前系统更像“可运行原型”，而不是“可切换模型、可回放、可分析、可治理”的平台骨架。

## Dify 值得借鉴的设计经验

### 1. 把“执行过程”当成一等公民，而不是临时副产物

Dify 不是只存用户问题和模型回答。它会把一次 workflow run、run 中每个 node 的执行、以及 agent 过程中的中间状态分开建模。

对 Drucker 的启发：

- 不要只存最终 answer
- 不要只靠 stdout 日志排查问题
- 要让系统天然知道“这次运行做了什么，经过了哪些步骤，在哪一步失败，花了多少 token 和时间”

这不等于必须上 workflow 画布，而是说明系统内部最好有明确的：

- Session / Conversation
- Message
- Run / Execution
- Step / ToolCall / Thought

这些对象一旦分清，后续回放、分析、重试、审计都会容易很多。

### 2. 业务层不要直接依赖厂商协议，要依赖平台自己的统一语义

Dify 内部并不是以 OpenAI 请求体作为第一抽象，而是先定义自己的模型消息、模型能力、返回结果、工具调用等统一对象，再由 provider 层去做适配。

对 Drucker 的启发：

- Agent 不应该直接认识 `AsyncOpenAI`
- Agent 不应该直接处理某厂商特有的 chunk 字段
- Agent 不应该直接绑定某厂商的 tool-call 返回格式

更好的做法是先定义平台自己的抽象，例如：

- `ChatMessage`
- `ModelRequest`
- `ModelResponse`
- `ToolCallEvent`
- `ReasoningEvent`
- `Usage`

这样模型切换的影响才会被收缩在 provider adapter，而不是扩散到每个 agent 和主流程。

### 3. Provider 管理要是独立能力，不要散落在业务代码里

Dify 在 provider 管理上做得比较“平台化”：provider 元信息、模型列表、凭证、默认模型、租户级配置、可用状态，都是单独管理的。

对 Drucker 的启发：

- 模型选择不该只是一个配置项字符串
- 不同 provider 的凭证和模型能力，不该直接散落在 agent 代码里判断
- 模型是否可用、默认用哪个模型、是否允许切换，最好有统一入口

即使 Drucker 现在不做复杂后台，也建议把以下几件事抽出来：

- provider registry
- model capability metadata
- credential/config resolution
- model selection policy

### 4. 大量运行数据不要强塞在单一对象里

Dify 会把不同层级的数据拆开，必要时还会对大 payload 做 offload，而不是把所有内容都塞进一条 message 或一张表。

对 Drucker 的启发：

- 用户可见内容是一类数据
- 调试/追踪数据是一类数据
- 厂商原始返回是一类数据
- 工具输入输出又是另一类数据

这些数据的用途、生命周期、查询方式都不同，最好不要混成一个 blob。

### 5. 观测体系要和业务执行解耦

Dify 的一个重要思路是：执行归执行，观测归观测。状态持久化、成本统计、trace 导出、日志展示不是同一个模块硬做完的。

对 Drucker 的启发：

- SSE 输出只是前端消费通道，不应该承担系统真实状态存储职责
- stdout logger 只能辅助排查，不能替代运行记录
- tracing 最好是附加能力，不要绑死在主执行循环里

## 哪些不要学

### 1. 不要照搬 Dify 的具体模型调用实现

Dify 本身是历史演进出来的平台，里面会有兼容包袱、旧接口、旧参数、旧调用习惯。尤其在 OpenAI 相关调用上，不适合直接当“现代最佳实践”照抄。

### 2. 不要为了学习它而引入过重的平台复杂度

Dify 的设计服务于多租户、低代码、插件化、工作流编排平台。Drucker 如果当前目标更聚焦，就不需要一开始引入完整的 workflow engine、复杂 provider 后台或庞大的 trace 系统。

### 3. 不要把“平台化分层”误解成“必须很多抽象层”

要学的是边界清晰，不是层数越多越好。只要能把模型接入、执行状态、消息会话、观测日志分开，就已经比当前状态前进很多。

## 对 Drucker 最有价值的三个借鉴点

### 1. 建立稳定的执行对象模型

最值得优先明确的是：

- session
- message
- run
- step

这套对象模型是后续持久化、观测、回放和调试的基础。

### 2. 建立统一模型抽象，而不是继续绑定 OpenAI 语义

真正的目标不是“兼容更多厂商”，而是“让业务代码不关心厂商”。只有先把平台自己的请求/响应语义立住，模型切换成本才会下降。

### 3. 把编排、执行、输出拆开

当前 `chat_stream` 一类方法同时承担：

- 推理循环
- 工具执行
- 厂商响应解析
- SSE 输出

这会让任何改动都变成核心手术。Dify 的经验说明，这几类职责拆开后，系统才更容易演进。

## 一个务实判断

如果只从“成熟传统平台设计”角度看，Dify 给 Drucker 的真正参考价值是：

- 如何定义稳定边界
- 如何把执行过程持久化
- 如何隔离 provider 差异
- 如何让系统具备分析和治理能力

而不是：

- 某个 API 参数怎么传
- 某个 SDK 怎么组织
- 某个老接口是否继续沿用

换句话说，Dify 可学的是“骨架”，不是“皮肤”。
